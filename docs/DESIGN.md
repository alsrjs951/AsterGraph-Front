# AsterGraph 디자인 시스템 및 제품 경험

작성일: 2026-11-01 · 기준: [ASTERGRAPH_VALUE_FIRST_SPEC.md v2.0](../ASTERGRAPH_VALUE_FIRST_SPEC.md)

이 문서는 LINK MARKET의 물류 장애를 분석하는 실제 동작형 로컬 목업의 디자인 기준이다. 최상위 기준은 v2.0 명세서이며, 디자인 선택이 충돌하면 명세서를 따른다. 최초 설계 단계에서는 문서만 작성했으며, 2026-11-01의 후속 구현 요청으로 실제 로컬 프론트엔드 구현과 검증을 완료했다. 실측 결과는 [VERIFICATION.md](./VERIFICATION.md)를 참고한다.

## 1. 확인한 프로젝트와 설계 범위

- 최초 설계 시 프로젝트 루트 전체와 숨김 파일을 확인했다. 당시 제품 파일은 `ASTERGRAPH_VALUE_FIRST_SPEC.md`뿐이다. `.DS_Store` 외 기존 앱 코드, `package.json`, Git 저장소, 하위 `AGENTS.md`, v1.0 문서, 기존 디자인 시스템은 없다.
- 아래 화면·컴포넌트·토큰은 빈 프로젝트에서 설계한 기준이다. 후속 구현 및 실제 렌더링 검수에 따른 조정은 §14와 VERIFICATION.md에 기록한다.
- 사용자는 이커머스 운영 담당자와 운영 책임자로 설정한다. 핵심 업무는 장애의 영향 주문을 식별하고 대체 출고 대상과 고객 안내 우선 대상을 구분하는 것이다.
- 시연은 파트너에게 향후 제품 콘셉트를 설명한다. 실제 고객 성과, 실시간 연동, 실제 AI 추론을 주장하지 않는다.
- Overview, Operations Intelligence, Ontology Explorer, Data Sources, End Card를 다룬다. 변경 관리, 온톨로지 편집, 권한 관리, 실제 주문 실행 기능은 추가하지 않는다.

## 2. Visual Concept: 근거가 붙은 운영 판단

**하나의 장애에서 출발해, 영향의 크기와 그 이유를 읽고, 대응 가능한 주문을 분리하는 작업대.**

운영 책임자가 기억해야 할 장면은 거대한 그래프가 아니라 **38건 중 26건은 대체 출고 가능하고, 12건은 고객 안내가 우선이라는 판단**이다. 가장 강한 시각적 표현은 같은 기준으로 정렬된 `38 → 12` 비교에 쓴다. 주변 탐색과 시스템 정보는 차분하게 유지한다.

### 2.1 최초 방향과 검토 결과

| 검토안 | 정보 구조 | 판단 |
|---|---|---|
| A. 대시보드 중심 | KPI 카드 → 여러 차트 → 별도 분석 화면 | 장애와 주문별 이유가 분리되어 30초 안에 판단 흐름을 전달하기 어렵다. 채택하지 않음. |
| B. 채팅 중심 | 질문·답변 대화열 → 근거 팝업 | 사용자가 결과와 근거를 동시에 비교하기 어렵다. 채택하지 않음. |
| C. 업무 분석 작업대 | 상황·질문 / 결과·대응안 / 선택 주문의 근거 | 동일한 화면에서 질문, 결과, 판단 이유를 연결할 수 있다. 최종 채택. |

```text
A  [KPI][KPI][KPI]       B  [질문             ]
   [차트][차트][차트]       [답변             ] [근거 팝업]

C  [상황과 질문] [38 영향 | 26 대체 가능 | 12 우선 대응]
   [분석 가정  ] [주문 목록 / 대응 전후 비교] [선택 주문의 근거]
```

초기 KPI 카드 반복안은 하나의 연결된 결과 띠로 수정했다. 이 세 수치는 독립 성과가 아니라 `38 = 26 + 12`의 분해이기 때문이다. 그래프는 자유롭게 떠다니는 네트워크 대신 주문별 고정 경로로 수정했다. 기술 탐색보다 판단 이유를 빨리 읽는 것이 우선이다. 모달 형태의 시뮬레이션은 중앙 영역 내 전환으로 수정하여 근거와 비교를 동시에 유지한다.

### 2.2 디자인 원칙

1. **숫자에는 대상과 조건을 붙인다.** `38건 영향`, `26건 대체 출고 가능`, `12건 우선 대응 필요`. 숫자만 띄우거나 26건을 처리 완료로 표현하지 않는다.
2. **위치는 유지하고 내용만 바꾼다.** 주문 선택 시 오른쪽 근거만, 계획 미리보기 시 중앙 하단만 바뀐다.
3. **색은 판단 상태에 쓴다.** 블루는 선택·분석, 틸은 대체 가능, 코랄은 잔여 위험. 카드마다 색을 배정하지 않는다.
4. **관계를 읽을 수 있게 만든다.** 연결선, 노드 이름, 재고 수량, SKU 조건을 함께 제시한다.
5. **한 상태에는 주 행동 하나를 강조한다.** 질문 단계는 `영향 분석`, 결과 단계는 `대응안 시뮬레이션`이다.
6. **원본과 계획을 구분한다.** 계획을 열어도 주문·재고 원본은 바뀌지 않으며, 결과에는 `시뮬레이션 결과`를 붙인다.

## 3. 제품 IA와 화면 역할

사이드바 순서는 명세서대로 `Overview`, `Operations Intelligence`, `Ontology Explorer`, `Data Sources`다. 일반 진입의 기본 화면은 Operations Intelligence, `30초 데모 시작`의 첫 화면은 Overview다. 두 진입을 구분한다.

| 화면 | 사용자가 알아야 할 것 | 주요 내용과 동작 |
|---|---|---|
| Overview | LINK MARKET의 부산 센터가 48시간 중단된다 | 경고, 질문 `어떤 주문이 영향을 받을까?`, OMS/WMS/PIM/TMS 4개 시스템 카드, `영향 분석하기` |
| Operations Intelligence | 어떤 주문에 영향이 있고, 무엇을 먼저 할 것인가 | 질문 → 38/26/12 → 주문 선택과 근거 → 38→12 비교 |
| Ontology Explorer | 분석의 배경에 어떤 업무 관계가 있는가 | 6개 개념과 최소 6개 관계, 노드 선택 시 설명·시스템 매핑. 읽기 전용. |
| Data Sources | 어떤 목업 시스템의 개념을 연결했는가 | 4개 시스템, 매핑된 개념, `DEMO CONNECTED`, 로컬 목업 설명 |
| End Card | 제품의 가치와 이름 | AsterGraph, `데이터를 연결하고, 결정을 앞당기다.`, `Enterprise Ontology Platform` |

상단에는 AsterGraph, `LINK MARKET · Enterprise Workspace`, `DEMO · SIMULATED DATA`, `Ontology v1.2 · Managed`를 유지한다. 좁은 화면에서는 워크스페이스명을 두 줄로 배치할 수 있지만 Demo 배지는 생략하지 않는다. Managed 상태의 설명은 `목업 시연 설정이며 실제 온톨로지 구축 완료를 뜻하지 않습니다`다. End Card에서도 Demo 배지는 같은 화면 모서리에 유지한다.

시스템 매핑 설계: OMS = Order·OrderItem, WMS = Warehouse·Inventory, PIM = Product, TMS = Shipment. 이것은 로컬 데모 모델이며 실제 커넥터나 API 상태가 아니다.

## 4. 타이포그래피

외부 폰트 요청 없이 시스템 sans-serif를 사용한다. 기본 스택은 `-apple-system, BlinkMacSystemFont, "Segoe UI", "Apple SD Gothic Neo", "Malgun Gothic", sans-serif`다. 타이틀과 데이터에 별도 장식 서체를 섞지 않는다. 브랜드는 텍스트 워드마크로 시작한다.

| 토큰 / 역할 | 1920×1080 | 1440×900 | 굵기 / 행간 |
|---|---:|---:|---|
| `display.compare` 전후 핵심 숫자 | 64px | 56px | 650–700 / 1.05 |
| `display.kpi` 38·26·12 | 48px | 40px | 650–700 / 1.1 |
| `title.page` 화면 제목 | 28px | 24px | 600 / 1.25 |
| `title.section` 패널 제목 | 20px | 18px | 600 / 1.35 |
| `body` 질문·판단 이유·주문 내용 | 18px | 16px | 400–500 / 1.5 |
| `label` 버튼·필터·주요 노드 | 16px | 16px | 500–600 / 1.4 |
| `meta` 기술 관계명·단위 보조·배지 | 14px | 14px | 400–500 / 1.4 |
| `caption.demo` 영상 자막 | 32px | 28px | 600 / 1.35 |
| `brand.end` 엔딩 제품명 | 56px | 48px | 600 / 1.1 |

- 숫자는 tabular figures, KPI의 `건`은 18px/16px로 숫자 기준선에 맞춘다. 표 숫자는 오른쪽, 제목·질문·설명·식별자는 왼쪽 정렬한다.
- 본문 자간은 기본값, 큰 숫자만 최대 -0.02em. 광범위한 대문자나 자간 확장은 쓰지 않는다. 명세서의 고정 배지 `DEMO · SIMULATED DATA`, `DEMO CONNECTED`는 예외다.
- 설명 한 문단은 2~3줄, 한 줄은 최대 약 70자. 근거의 핵심은 짧은 문장 2개로 먼저 제시한다.
- 핵심 질문, KPI 레이블, 주문번호, SKU, 재고 수량, 비교 레이블에는 말줄임표를 사용하지 않는다. 공간이 부족하면 줄을 바꾸거나 보조 정보를 접는다.
- 녹화에서는 브라우저 확대율 100%, 폰트 로딩 완료 상태를 고정한다. 시스템별 글꼴 폭 차이는 두 목표 해상도에서 따로 확인한다.

선정한 불투명 색상 쌍을 계산한 결과, `surface.raised` 위 기본/보조/뮤트 텍스트는 각각 약 13.37:1 / 7.88:1 / 5.93:1이다. 블루·틸·코랄 텍스트는 6.39:1 / 8.42:1 / 7.38:1, control 경계는 3.90:1이다. 블루 CTA 위 네이비 텍스트는 8.02:1이다. 실제 구현의 혼합 색상·투명도·hover 상태는 다시 검사해야 한다.

모든 정상 텍스트는 4.5:1 이상, 의미 있는 경계와 그래프 선은 3:1 이상을 목표로 한다. 색만으로 의미를 전달하지 않으며 `대체 가능`, `우선 대응`, `선택됨` 텍스트나 형태 표시를 병행한다. 틸 체크 표시를 쓰더라도 `출고 완료`를 암시하지 않도록 반드시 가능 상태 레이블을 붙인다.

## 6. 그리드·간격·영역 예산

모든 치수는 CSS px, 브라우저 콘텐츠 뷰포트 기준이다. 4px 기본 단위, 주요 간격은 8/12/16/24/32/48px을 사용한다. 녹화 환경은 브라우저 툴바를 제외한 콘텐츠가 목표 해상도가 되도록 설정한다.

### 6.1 가로 예산

| 항목 | 1920×1080 | 1440×900 |
|---|---:|---:|
| 사이드바 | 216 | 192 |
| 본문 좌우 여백 | 각 32 | 각 24 |
| 본문 사용 폭 | 1640 | 1200 |
| 상황·질문 열 | 272 | 216 |
| 중앙 결과 열 | 840 | 536 |
| 오른쪽 근거 열 | 480 | 416 |
| 열 사이 간격 | 각 24 | 각 16 |

예: 1440에서 `192 + 24×2 + 216 + 536 + 416 + 16×2 = 1440`. 1440~1920 사이는 이 기준 사이에서 유동 배치하고, 본문을 단순 확대·축소하지 않는다. 1920보다 넓으면 작업 영역 최대 폭 1640을 유지한다.

### 6.2 세로 예산: 녹화 모드

| 항목 | 1920×1080 | 1440×900 |
|---|---:|---:|
| 앱 헤더 | 72 | 64 |
| 화면 제목·상태 행 | 80 | 64 |
| 작업 영역 위 간격 | 24 | 16 |
| 작업 영역 높이 | 752 | 624 |
| 자막 위 간격 | 24 | 16 |
| 자막 전용 영역 | 96 | 80 |
| 아래 안전 여백 | 32 | 36 |
| 합계 | 1080 | 900 |

작업 영역에서 왼쪽 열은 전체 높이를 사용한다. 중앙+오른쪽 위에는 연결된 KPI 띠(144/128px), 아래에는 간격(24/16px)을 두고 목록·근거(584/480px)를 나란히 배치한다. 패널 내부 여백은 1920에서 24px, 1440에서 16px이다. 자막은 별도 영역이므로 버튼·주문 행을 가리지 않는다.

일반 조작 모드는 자막 영역을 재생 컨트롤 영역으로 사용한다. Record Mode에서는 같은 영역에 자막을 보여주고 컨트롤을 숨긴다. 디버그 정보는 녹화에서 제거한다. 숨긴 영역만큼 핵심 콘텐츠를 재배치하지 않아 촬영 전후 구도가 유지된다.

### 6.3 적응형 규칙

- 두 목표 해상도의 핵심 장면은 문서·패널 스크롤 없이 읽는다. 모든 38개 주문을 한 화면에 넣는다는 뜻은 아니다. 목록은 페이지 방식으로 전체를 조회한다.
- 1280~1439px에서는 왼쪽 상황·질문을 위쪽 펼침 영역으로 옮기고 결과·근거 2열을 유지한다. 글씨를 줄여 3열을 강제하지 않는다.
- 768~1279px에서는 결과 아래 근거를 배치한다. 더 작은 화면에서는 세로 1열, 메뉴 버튼으로 탐색을 제공한다. 목록은 핵심 필드가 있는 행 단위로 재구성하며 가로 스크롤을 만들지 않는다.
- 작은 화면과 텍스트 확대에서는 세로 스크롤을 허용하고 정보 접근성을 우선한다. 30초 촬영 보장은 두 목표 뷰포트·100% 확대율 범위다.

### 7.2 대응안 미리보기: 19~27초

KPI와 질문·선택 주문 근거는 유지한다. 중앙의 목록 영역만 다음 내용으로 교체한다.


26건·12건 대응 카드는 하나의 분할된 계획 영역으로 묶는다. 외부로 주문을 보내거나 고객에게 알리는 버튼은 없다. 여기서 의사결정은 **검토할 대응 대상과 우선순위를 얻는 것**이다. 새로운 승인·발송·실행 워크플로를 만들지 않는다.

1440의 중앙 536×480px 내에는 내부 여백 32px, 제목 24px, 비교 104px, 막대 64px, 대응 카드 128px, 설명·해제 68px, 사이 간격 합계 60px을 배정한다. 합계 480px이다. 대응 카드는 각 64px 행 안에서 왼쪽에 제목·짧은 조건, 오른쪽에 44px 높이의 대상 보기 버튼을 둔다. 예를 들어 조건은 `서울 SKU_A 26개`로 압축한다. 레이블은 최대 두 줄로 감싸고, 상세 가정은 별도 설명 영역에서 열어 핵심을 밀어내지 않는다. 구현 시 실제 글꼴로 맞지 않으면 카드 보조 문구부터 줄이며 핵심 숫자·레이블은 유지한다.

## 8. KPI·비교·목록 규칙

### 8.1 세 KPI

- 하나의 수평 띠를 3개 구역으로 나누고 얕은 구분선만 사용한다. 각 구역에는 레이블, 큰 숫자, 필요 시 한 줄 조건을 배치한다.
- 영향 38은 밝은 중립색, 대체 가능 26은 틸, 우선 대응 12는 코랄. 선택 상태는 별도의 블루 밑줄과 눌림 상태로 표현해 의미 색상과 구분한다.
- KPI 전체가 필터 버튼이다. 클릭 시 해당 목록을 표시하고 목록 제목·건수·선택 상태를 함께 갱신한다. 계획 보기 중 KPI 클릭은 계획 상태를 유지한 채 필터 목록으로 이동한다.
- 영향 총수는 시뮬레이션 후에도 38이다. 12를 새로운 영향 총수처럼 덮어쓰지 않는다.

### 8.2 전후 비교

- 동일한 모집단의 위험 건수 비교다. 두 가로 막대는 같은 시작점·같은 길이 척도(0~38건)를 사용한다. 아래 막대는 위 막대의 12/38 길이다.
- 상단은 `조치 전 지연 위험 38건`, 하단은 `대체 출고 계획 적용 후 잔여 위험 12건`으로 직접 표기한다. 위험 막대는 같은 코랄을 사용한다. 감소 자체를 출고 완료로 표현하지 않는다.
- 26은 별도 대응 카드에서 `대체 출고 제안`으로 설명한다. 도넛, 게이지, 의미 없는 상승 추세 차트를 추가하지 않는다.
- 68.4%는 기본 화면에서 생략한다. 추후 표시하더라도 `시뮬레이션상 대체 출고 가능 비율`만 허용한다.
- 화면 읽기 대체 문장: `영향 주문 38건 중 26건에 대체 출고를 가정하면 잔여 지연 위험은 12건입니다.`

### 8.3 주문 목록

고정 열은 `주문`, `상품`, `대응 분류`다. 전체가 부산 할당 주문이므로 각 행에 부산을 반복하지 않고 목록 설명에 표시한다. 수량 1과 납기 가정은 근거·가정 영역에서 확인한다. 별도 금액·매출·고객 실명은 만들지 않는다.

- 필터는 `전체 영향(38) / 대체 출고(26) / 우선 대응(12)`이며 필터와 KPI는 같은 상태를 공유한다.
- 정렬은 주문번호 오름차순. 1440에서는 페이지당 6행, 1920에서는 7행, 행 높이는 각각 48/52px이다. 페이지 상태를 표시하고 처음·끝의 이동 버튼은 비활성화한다.
- 주문번호는 실제 버튼이다. 행 클릭과 버튼의 Enter 모두 같은 선택 동작을 호출한다. 선택 행은 배경+왼쪽 표시+접근 가능한 선택 상태를 제공한다.
- 필터 변경 시 첫 페이지로 이동한다. 기존 선택 주문이 필터 안에 있으면 유지하고 해당 페이지를 보여준다. 없으면 새 결과의 첫 주문을 선택한다. 초기 분석 완료 시에는 선택하지 않고 대표 주문 클릭을 안내한다.
- 전체/대체 목록 첫 페이지에 LM-1001, 우선 대응 첫 페이지에 LM-1027이 나온다. 대표 사례를 보이기 위해 별도 복제 행을 만들지 않는다.
- 빈 결과에는 `조건에 맞는 주문이 없습니다`와 `전체 영향 보기`를 제공한다. 고정 seed의 기본 필터에서는 빈 결과가 생기지 않는다.

목록 패널의 높이 예산은 1440에서 여백 32 + 제목 24 + 필터 44 + 열 제목 24 + 6행 288 + 페이지 제어 44 + 간격 합계 24 = 480px이다. 1920에서는 여백 48 + 제목 28 + 필터 44 + 열 제목 24 + 7행 364 + 페이지 제어 44 + 간격 합계 32 = 584px이다. 목록 설명은 별도 행을 늘리지 않고 제목 옆에 배치한다.

## 9. 판단 근거 그래프

### 9.1 구조와 의미

선택 주문마다 주 경로는 **Warehouse → Inventory → Product → OrderItem → Order**의 5개 노드다. 이 화살표는 사용자의 탐색 순서다. 원래 관계의 저장 방향과 혼동하지 않도록 실제 edge 방향과 관계명은 별도로 보존한다.

| 실제 관계 방향: 제안 모델 | 업무 해석 |
|---|---|
| Inventory —storedAt→ Warehouse | 해당 재고를 보관하는 센터 |
| Inventory —stockOf→ Product | 해당 재고의 상품 |
| OrderItem —referencesProduct→ Product | 주문 항목이 참조하는 상품 |
| Order —containsItem→ OrderItem | 주문에 포함된 항목 |
| Order —allocatedFrom→ Warehouse | 원래 할당된 출고 센터 |
| Order —fulfilledBy→ Shipment | 주문에 연결된 배송 목업 정보 |

명세서가 관계 이름만 정의한 부분의 도메인·방향은 위와 같이 제안한다. seed 확정 시 타입과 설명을 함께 고정한다. 설명용 탐색 순서를 맞추려고 실제 edge를 반대로 저장하지 않는다.

선택 SKU의 서울 Inventory와 서울 Warehouse 2개를 오른쪽 분기로 추가해 최대 7개 노드를 쓴다. 0개 재고도 Inventory 노드를 유지한다. 전체 120건 그래프를 렌더링하거나 force layout으로 노드를 떠다니게 하지 않는다.

1440의 근거 패널에서는 5개 주 노드를 세로로 고정하고, 서울 재고·센터는 Product 옆 분기로 정렬한다. 노드 높이 44px, 주 노드 간격 16px로 그래프 높이 284px을 확보한다. 기술 관계명은 보조 14px, 노드의 업무 이름과 수량은 16px이다. 부가 관계명이 겹치면 노드 상세에 표시하고 핵심 경로와 수량을 우선한다. 노드 선택은 설명을 바꾸며 그래프 위치를 바꾸지 않는다.

### 9.2 대표 주문의 근거 문구

| 주문 | 기본 근거 | 서울 대체 조건 | 결론 |
|---|---|---|---|
| LM-1001 | 부산 할당·PENDING·SKU_A·수량 1 | SKU_A 일치, 서울 가용 26개, 주문번호 순 배정으로 1개 가능 | `서울 센터에서 1개 대체 출고 가능` |
| LM-1027 | 부산 할당·PENDING·SKU_B·수량 1 | SKU_B 일치, 서울 가용 0개, 배정 0개 | `대체 재고가 없어 고객 안내 우선 대상` |

재고 26은 계획 전 가용 수량이다. LM-1001에 26개를 배정한다는 뜻이 아니다. 근거에는 `가용 26개 중 이 주문 1개 배정 가능`을 명시한다. 시뮬레이션 화면에서도 원본 재고 26을 0으로 덮어쓰지 않는다.

기본 선은 control 색, 선택한 주 경로는 블루, 서울 대체 분기는 틸 또는 코랄과 가능/불가 텍스트를 함께 사용한다. 해당 노드와 연결만 한 번 강조하고 전체 그래프를 점멸시키지 않는다. Shipment는 Ontology Explorer에 포함하되 이 핵심 근거 패널에는 노드 수를 늘려 추가하지 않는다.

그래프 아래에 선택 주문의 결과 설명을 제공하고, 노드 클릭·키보드 선택으로 개념·관계·시스템 매핑을 확인한다. 같은 내용을 순서 있는 텍스트 경로로도 제공한다. hover는 보조 설명이며 유일한 접근 방법이 아니다.

| 계산 불일치·예상 밖 오류 | 숫자를 대신 채우지 않고 `데모 상태를 다시 불러와 주세요`와 `리셋` 제공. 외부 서버 연결 실패처럼 표현하지 않음. |

분석 가정의 요약은 `48시간 장애 · 주문당 상품 1개 · 목업 재고 기준`이다. `가정 보기`에서 동일 납기 판단 구간, 서울 출고 가능 가정, 실제 운송 시간·도로 상황·비용·SLA·재고 예약·현실 우선순위 미반영을 설명한다. 계획은 이 조건에서의 결과임을 본문에도 붙인다.

LM-1027은 수동 탐색·검증에서 반드시 확인한다. 12~19초 자동 시연은 명세서의 LM-1001 사례에 집중하고 두 사례를 빠르게 번갈아 보여주지 않는다. 4~7초 연결 표현은 시스템 이름과 업무 개념의 연결 요약이며, 전체 관계 모델은 근거 그래프·Explorer에서 확인한다.

### 모션 토큰

| 동작 | 시간 | 처리 |
|---|---:|---|
| hover·선택 피드백 | 200ms | 색·opacity만, 클릭 효과는 즉시 인지 가능하게 시작 |
| 화면 전환 | 250ms | 공통 헤더 유지, 내용 crossfade |
| 주문 근거 강조 | 300ms | 선택 경로·분기의 강조만 변화, 카메라 이동 없음 |
| 비교 영역 전환 | 300ms | 같은 위치에서 내용 교체, 최종 숫자는 즉시 읽을 수 있게 표시 |
| 시스템 관계 연결 | 450ms | 한 번만 opacity로 순서 표현, 반복 입자 없음 |
| 분석 피드백 | 600ms | 비즈니스 상태 대기. 실제 LLM 처리시간으로 주장하지 않음. |

일반 전환은 ease-out 계열, 퇴장은 더 짧게 한다. 프레임마다 레이아웃 치수를 바꾸지 않는다. 숫자 카운트업, 과도한 줌, 행별 연쇄 등장, 자막 타자 효과는 사용하지 않는다. 애니메이션 종료 이벤트가 비즈니스 상태를 결정하지 않으며 중단·장면 이동 시 최종 상태로 수렴한다.

`prefers-reduced-motion`에서는 타이핑·경로 전개·crossfade를 생략하고 같은 시각의 최종 내용을 표시한다. 6개 장면의 시간 경계는 유지한다. 분석 대기 중에는 정적인 진행 문구를 제공한다.

## 12. 재생·녹화·접근성 기준

- 일반 모드에 `30초 데모 시작`, `일시정지/재개`, `리셋`, 이전/다음 장면, 6개 장면 선택을 제공한다. 자동 시작하지 않는다.
- 자동 재생 중 일반 UI를 직접 조작하면 먼저 일시정지한다. `재개`는 현재 시각에 해당하는 결정적 데모 상태를 복원하고 이어간다. 수동 탐색 상태와 자동 타임라인이 경쟁하지 않게 한다.
- Record Mode는 디버그·재생 컨트롤을 숨긴다. 진입 전에 단축키 안내를 읽을 수 있게 하고 `Esc`로 녹화 모드를 빠져나와 제어를 복원한다. Demo 배지는 숨기지 않는다.
- 입력 요소에 focus가 없을 때만 `Space`, `R`, `←/→`, `1–6` 단축키를 처리한다. IME 입력과 브라우저·보조기기 단축키를 침범하지 않는다.
- 전체 UI는 키보드로 조작 가능해야 한다. focus가 항상 보이며 자막·팝오버가 가리지 않게 한다. 그래프를 드래그하지 않아도 근거를 읽을 수 있다.
- 시연 중 자막은 한 줄을 목표로 하고, 1440에서 엔딩 문구만 필요 시 두 줄 허용한다. 본문에 같은 문장을 중복하여 두 번 크게 표시하지 않는다.
- 1920 녹화 프레임을 75% 크기로 검토해도 핵심 수치·조건·레이블을 읽을 수 있어야 한다. 이는 실제 렌더·녹화 후 수행할 검수 기준이며 현재 검증 완료를 뜻하지 않는다.
- 외부 폰트·이미지·CDN·분석 API 없이 재현한다. 이름·아이콘·배지는 로컬 렌더링한다.

## 14. 제품 디자인 리뷰 및 polish 반영

2026-11-01, Impeccable의 독립 비평과 렌더링 검수 후 기존 네이비 작업대의 정체성을 유지하며 정교화했다. 제품 범위, seed, 분석 함수와 30초 타임라인은 그대로다.

- **§2·§3 영향/근거:** 실제 edge 방향을 유지하고 노드 사이에 `보관 위치`, `재고 상품`, `상품 참조`, `주문 구성`을 표시한다. 기술 관계명과 출처는 노드 상세에 남긴다. 44px 노드와 16px 연결 간격은 유지하며, 조밀한 그래프의 선택·키보드 초점 링은 노드 내부에 표시해 관계 레이블을 가리지 않는다.
- **§2·§4 전후 비교:** 두 비교 레이블을 두 줄로 맞추고 38/12의 기준선을 정렬한다. 같은 척도의 코랄 막대는 유지하며, 두 대응 행의 26/12를 두 번째 읽기 순서로 강조한다. 중첩된 외곽 테두리는 구분선으로 정리한다. 작은 데스크톱에서 비교 패널 간격은 8px, 큰 녹화 화면에서는 16px로 조정해 글자 크기를 보존한다.
- **§5 상태·조작:** 질문 안내는 대기/분석/완료/미리보기 상태를 따른다. 목록 제목은 선택 필터와 건수를 표시한다. 계획 적용 중 왼쪽 CTA는 `계획 비교 보기`이며, 해제는 비교 영역 하단 한 곳에 둔다. 내부 화면 전환은 오른쪽 화살표로 표시하고 KPI에는 필터 동작 표시를 추가한다.
- **§6 가독성:** 결과 건수, 그래프 관계·상세, 비교 조건과 대응 행의 보조 정보는 14px 메타 토큰을 사용한다. 숫자·노드의 주요 계층과 기존 의미 색상은 유지한다. 커서와 텍스트 선택 색상도 동일 팔레트를 따른다.
- **§3 보조 화면:** Ontology Explorer는 실제 관계 목록을 렌더링하고 선택 개념의 연결만 강조한다. Order→Shipment 경로는 OrderItem 아래를 우회해 거짓 연결처럼 보이지 않게 한다. Data Sources는 높이 999px 이하 데스크톱에서 간격과 패딩을 줄여 소스 카드·안내가 시연 컨트롤과 겹치지 않게 한다.

검증과 남은 한계는 [VERIFICATION.md](./VERIFICATION.md), 비평 근거와 우선순위는 [DESIGN_REVIEW.md](./DESIGN_REVIEW.md)에 기록한다.

## 15. 로고와 라이트·다크 테마

사용자의 후속 요청으로 라이트 모드를 추가했다. 기존 다크 네이비는 기본값이며, 색상 선택은 데이터·분석·재생 상태와 독립적인 표시 설정이다.

### 로고

사용자가 확정한 **AG Aperture(A안)**를 적용했다. A의 둥근 삼각 실루엣과 G의 열린 입구를 하나의 윤곽으로 합쳤다. 이전의 겹치는 연결선과 사각 노드는 제거했다. SVG로 제작해 작은 헤더와 큰 엔딩에서 선명하게 표시한다. 마크와 워드마크를 함께 사용하는 사이드바, 브랜드를 기억시키는 엔딩, 브라우저 탭 아이콘에 배치한다. 모바일에서는 사이드바 대신 헤더에 마크를 표시한다. 분석 결과·KPI·근거 그래프 내부에는 반복 삽입하지 않는다.

- 사이드바 마크: 32px, 좁은 데스크톱 28px. 워드마크는 자간을 조정한 Manrope 560의 윤곽선 SVG이며 외부 폰트 요청이 없다. 접근성 이름은 AsterGraph다.
- 엔딩 마크: 96px, 그 아래 AsterGraph 워드마크. 제품 슬로건과 기존 타임라인 유지.
- 독립 에셋: `public/astergraph.svg`(어두운 바탕), `public/astergraph-light.svg`(밝은 바탕), 투명 배경.
- 앱 내 마크는 공통 BrandMark 컴포넌트로 렌더링하며 테마의 블루 단색을 따른다. 다크용은 내부 여백을 보정하고, 16–24px 파비콘은 입구를 24→32 단위로 확장했다. 워드마크는 테마의 Ink 색상이다.
- 최종 심볼·가로형·세로형·워드마크 SVG는 `public/brand/`, 아이콘·목업·가이드는 `docs/brand/astergraph-final/`에 있다. 상세 규칙은 [로고 가이드](brand/astergraph-final/GUIDELINES.md)를 따른다.

본문·보조 글자와 의미 색상 여섯 종류는 Raised 표면에서 4.5:1 이상을 브라우저 회귀 검사로 확인한다. 위험 배지, 선택, 버튼 hover, 대화상자·backdrop, 입력 커서, 그래프와 로고도 시맨틱 토큰을 사용한다.

헤더 오른쪽의 태양/달 버튼은 전환할 모드를 이름과 툴팁으로 알리고 44px 클릭 영역을 제공한다. 선택은 localStorage에 보관하며 초기 HTML에서 읽어 잘못된 테마가 먼저 나타나는 현상을 방지한다. 저장소 접근이 차단돼도 현재 세션 전환은 가능하다. 테마 변경은 자동 재생을 일시정지하지만 결과·선택 주문·계획을 초기화하지 않는다. Record Mode에서는 테마 버튼을 숨기고 선택한 모드와 Demo 배지는 유지한다.

## 16. 사용 가치에서 온톨로지 기반으로 마무리하는 엔딩

2026-11-01 사용자 후속 지시: 초반의 사용법·기업 가치 전달은 유지하고, 후반에는 그 모든 판단이 온톨로지 관리 구조에 기반한다는 인상으로 끝낸다. 최신 명세서의 27–30초 항목과 화면 E에 반영했다.

0–27초의 문제→질문→38/26/12→38→12 비교는 변경하지 않는다. 27–30초에 제목 **“모든 판단의 기반, 관리되는 기업 온톨로지.”**, 확정 로고, 읽기 전용 관계 모델을 한 화면에 배치한다. 왼쪽 그래프는 Ontology Explorer와 같은 `OntologyGraph` 컴포넌트 및 seed를 사용한다. 오른쪽은 원천 시스템 매핑, 공통 개념·관계 수, 영향 추적·대체 재고 검증·대응안 시뮬레이션의 활용 맥락을 설명한다. 개념 수와 관계 수는 배열 길이에서 계산한다.

네이비/라이트 시맨틱 토큰과 기존 시스템 글꼴을 유지한다. 제목은 28–42px, 그래프 노드는 16/14/12px의 개념·업무명·원천 순서다. 배경 장식 대신 하나의 모델 영역과 측면 설명을 사용한다. 노드를 누르면 관련 경로와 하단 설명이 바뀌며, `관계 모델 살펴보기`는 읽기 전용 Explorer를 연다. 단일 250ms 진입 모션만 적용하고 reduced-motion에서는 제거한다.

녹화 자막: **“이 모든 판단의 기반, 관리되는 기업 온톨로지”**. 3초 안에는 제목·모델·관리 상태의 연결을 전달하고, 자세한 설명은 정지하거나 수동 탐색할 때 읽도록 위계를 둔다. 음성 파일을 추가하지 않았으며 권장 짧은 내레이션은 “그 기반은, 관리되는 온톨로지.”다. 실제 관리 기능이나 백엔드가 운영 중이라는 주장은 하지 않는다.

## 17. 실제 업무 탐색을 위한 온톨로지 작업대

2026-11-01 후속 요청 반영. 엔딩의 온톨로지를 실제 기업 사용자가 탐색하는 제품 UI로 개선했다. 기존 테마·로고·업무 데이터·앞 27초는 유지하고, Explorer와 엔딩이 동일한 `OntologyWorkbench`를 사용한다.

- **문제:** 관계명 없는 연결선, 과도하게 큰 노드, 선택과 무관한 정적 설명으로는 데이터 구조를 검토하기 어렵다.
- **흐름:** 개념/시스템 검색 → 개념 선택 → 연결 관계 확인 → 관계 선택 → 연결된 개념으로 이동. `데이터 예시`는 기존 seed의 목업 값을 보여준다.
- **그래프:** 업무명 우선, 기술 식별자와 원천 시스템은 보조로 배치한다. 6개 관계 모두 한국어 의미와 방향을 노출하고 관계명 버튼을 키보드로 선택할 수 있다. 선택은 체크와 윤곽선으로도 구분한다.
- **필터:** 개념 이름·시스템 검색 및 원천 시스템 필터는 일치하지 않는 노드를 흐리게 표시한다. 모델 위치를 바꾸거나 개념을 삭제하지 않는다. Enter는 첫 검색 결과를 선택한다. 결과 없음 안내와 초기화를 제공한다. 연결 강조는 선택 개념의 직접 이웃을 강조한다.
- **상세:** 개념 정보/목업 데이터 예시 전환, 관계의 저장 방향·업무 의미·원천 시스템 표시. 연결 개념 버튼으로 탐색을 이어간다. 저장·편집·운영 상태 변경 버튼은 추가하지 않는다.
- **레이아웃:** 모델 제목/읽기 전용 상태, 탐색 도구, 그래프와 상세 패널, 버전/매핑 상태 순서. 엔딩의 브랜드 제목을 24px로 줄여 작업 영역을 확보했다. 1440/1920 기본 엔딩은 스크롤 없이 읽힌다. 상세 내용이 길면 상세 패널만 스크롤한다.
- **모바일:** 그래프를 억지로 축소하지 않고 개념을 2열 목록으로 제공하며 상세 패널의 관계 목록으로 이동한다. 1100px 이하에서는 세로 흐름을 사용한다.
- **시연:** 수동 탐색은 자동 시연을 일시정지한다. 장면 재진입/재개는 Inventory 기본 선택으로 복원된다. 총 30초와 마지막 메시지는 유지된다. 관리 상태는 로컬 목업임을 상태 행에 명시한다.
