## 1. 범위와 현재 상태

최초 설계 단계에서 프로젝트 루트와 숨김 파일을 검사했으며 명세서 외 앱 코드, 패키지 설정, Git 저장소, v1.0 문서, 기존 디자인 문서는 없었다. 따라서 기존 코드 재사용·마이그레이션 작업은 없다. 최초 단계에서는 두 설계 문서만 작성했다. 후속 구현 요청에 따라 아래 계획을 실행했으며, 현재 소스와 설치 버전은 프로젝트 파일 및 package-lock.json에 있다. 구현 결과와 실제 검증 증거는 [VERIFICATION.md](./VERIFICATION.md)를 참고한다.

목표는 실제 동작형 로컬 웹 목업으로 `문제 인지 → 자연어 질문 → 영향 분석 → 근거 확인 → 대응안 시뮬레이션 → 대응 대상 판단`을 정확히 30초에 시연하는 것이다. 가장 높은 구현·검수 우선순위는 12~27초의 Operations Intelligence다.

필수 범위: 네 화면과 End Card, 동일 데이터에서 산출한 38/26/12, 7노드 이하 근거, 전후 비교, 수동 상호작용, 자동 재생·복원, Record Mode, 두 목표 해상도.

제외 범위: 실제 DB·백엔드·LLM·ERP·배송 API, 실제 주문·재고 변경, 고객 알림 발송, 온톨로지 편집기·변경 관리·권한 시스템, 임의 질문에 대한 생성형 답변. 외부 서비스나 배포 작업도 이 프로토타입을 완성하는 데 필요하지 않다.

## 2. 기술 방향과 제안 구조

명세서 §7의 빈 프로젝트 권장안을 따라 **React + TypeScript + Vite + Tailwind CSS**를 후속 기본안으로 선택한다. 구현 착수 시에는 스택이 없었으며, 현재 권장 스택과 lucide-react, Vitest, Playwright를 설치했다. 실제 버전은 package-lock.json을 기준으로 한다.

- 화면·상태: React의 공용 reducer와 순수 selector로 충분하다. 별도의 서버 상태 라이브러리나 전역 이벤트 버스를 도입하지 않는다.
- 그래프: 5~7개 고정 노드는 SVG 연결선 + 키보드 접근 가능한 HTML 노드 버튼을 우선 검토한다. Explorer도 소규모 고정 레이아웃이다. `@xyflow/react`는 패닝·노드 관리 필요가 입증될 때만 선택한다. 자유 편집·drag 기능 때문에 추가하지 않는다.
- 아이콘: `lucide-react` 후보. 단일 계열만 사용하며 외부 URL에서 가져오지 않는다.
- 스타일: DESIGN.md의 시맨틱 토큰을 한 파일에서 정의하고 Tailwind와 연결한다. 컴포넌트별 원시 색상·임의 치수 반복을 피한다.
- 검증: 순수 함수 테스트용 Vitest, 실제 흐름·뷰포트 확인용 Playwright를 후보로 한다. 최소한 핵심 데이터·타임라인·상태 복원은 자동 검증한다.
- 모션: CSS opacity/transform 중심. 별도 애니메이션 프레임워크는 필요하지 않다.

## 3. 데이터 계약과 계산의 단일 기준

### 3.1 고정 seed

| 대상 | 필수 조건 |
|---|---|
| 주문 | LM-1001~LM-1120, 고유 ID 120개 |
| 직접 영향 | 부산 할당·PENDING 38건 |
| SKU_A 영향 | LM-1001~LM-1026, 26건, 각 1개 |
| SKU_B 영향 | LM-1027~LM-1038, 12건, 각 1개 |
| 비영향 | LM-1039~LM-1120, 82건, 부산 할당 아님 |
| 서울 대체 재고 | SKU_A 26개, SKU_B 0개 |
| 상품·센터 | SKU_A/B/C 3개, 부산·서울 2곳 |
| 가정 | 주문당 상품 1개·수량 1, 동일 납기 판단 구간, 서울의 26건 출고 가능 |

명세서가 정하지 않은 82건의 SKU 분포와 비핵심 재고는 영향 계산을 바꾸지 않는 결정적 값으로 정의한다. SKU_C도 seed에 포함한다. 난수·현재 시각·외부 데이터로 생성하지 않는다. 비핵심 숫자를 추가 성과 지표로 노출하지 않는다.

각 Order는 하나의 OrderItem을 가진다. Inventory는 센터·SKU 조합으로 고유하게 식별하고 0개 재고도 보존한다. 온톨로지 관계 방향은 DESIGN.md §9의 모델을 채택하여 관계 추적·시스템 매핑·설명이 일치하게 한다. Shipment는 보조 Explorer 관계를 위한 목업이며 실배송 진행을 뜻하지 않는다.

### 3.2 단일 분석 결과

분석 함수는 seed와 장애 조건을 받고 다음 정보를 한 결과 객체에 반환한다.

- 영향 주문 ID 집합과 영향 수 38.
- 주문번호 오름차순으로 SKU별 서울 가용 재고를 소비해 계산한 대체 가능 ID 집합 26.
- 영향 집합에서 대체 가능 집합을 뺀 잔여 위험 ID 집합 12.
- 각 주문의 원래 할당, 상태, SKU, 수량, 서울 가용 재고, 계획상 배정 수량, 판정 이유, 근거 노드·관계.
- 계획 전 위험 38, 계획 후 잔여 위험 12, 모델 가정.

KPI·필터·페이지 총수·주문별 그래프·비교 막대·대응 카드 모두 이 결과에서 파생한다. 화면별 38/26/12 상수를 두지 않는다. 타임라인에도 결과 숫자를 직접 넣지 않고 공용 분석 명령을 사용한다.

### 3.3 반드시 지킬 불변식

1. 전체 주문 120 = 영향 38 + 비영향 82.
2. 영향 38 = 대체 가능 26 + 잔여 위험 12. 두 부분집합은 겹치지 않는다.
3. SKU별 계획 배정은 서울 가용 재고를 초과하지 않는다. 다른 SKU 재고로 대체하지 않는다.
4. LM-1001은 SKU_A 1개 배정 가능, LM-1027은 SKU_B 0개로 불가다.
5. 분석·계획 미리보기·해제·재생·리셋 모두 seed의 주문·재고를 변경하지 않는다.
6. 동일 입력은 동일 순서·숫자·근거를 반환한다. 반복 실행 시 재고가 누적 차감되지 않는다.

## 4. 공용 상태·상호작용 설계

### 4.1 상태 소유권

| 상태 | 의미 / 기본값 |
|---|---|
| `activePage` | 일반 초기값 Operations Intelligence, 데모 시작 시 Overview |
| `scenarioActive` | 부산 48시간 중단 가정. 초기 true, 실운영 장애 감지 아님. |
| `queryText` / 입력 피드백 | 빈 입력에서 시작, 추천 질문으로 채움. 지원 여부는 로컬 정책으로 검증. |
| `analysisStatus` | idle / analyzing / done |
| `analysisResult` | 순수 함수 결과, 완료 전 null |
| `selectedOrderId` | 최초 null, 주문 클릭 또는 필터 변경 정책으로 설정 |
| `orderFilter` / `orderPage` | 전체 영향 / 첫 페이지 |
| `planPreviewApplied` | false, 주문 원본과 분리 |
| `resultsView` | orders / plan. 계획 활성 여부와 표시 화면을 구분. |
| `selectedEvidenceNodeId` | 근거의 선택 노드, 주문 변경 시 초기화 |
| `demoPlayback` | currentTime, playing, paused, currentScene |
| `recordMode` | 초기 false, 컨트롤·자막 표시 방식만 결정 |

재생 속도 변경은 명세서 선택 사항이며 첫 구현에서 생략한다. 1배속 30초의 신뢰성을 먼저 완성한다. 페이지·노드·모드 등의 추가 상태는 필수 기능을 위한 표시 상태이고 새로운 업무 기능이 아니다.

수동·자동 동작은 동일한 `질문 채우기`, `분석 요청/완료`, `주문 선택`, `필터 변경`, `계획 미리보기/해제`, `화면 이동` 명령을 사용한다. 자동 재생만 별도 JSX 결과를 출력하는 경로를 만들지 않는다.

지원 질문은 명세서의 고정 질문 한 개다. 앞뒤 공백·연속 공백 정도만 정규화하고 그 밖의 임의 질문에는 미지원 안내를 한다. 새로운 분석 능력을 가장하는 키워드 매칭을 추가하지 않는다. 추천 질문 버튼은 질문을 채우며 실행은 별도 버튼이 담당한다.

입력 편집 시 이전 결과·계획을 해제한다. 분석 중 중복 제출을 막으며, 리셋·장면 이동·새 입력 이후 이전 완료 이벤트는 세대 식별자로 무효화한다. 화면 탐색은 현재 분석 상태를 보존하고 리셋만 초기화한다.

## 5. 데모 타임라인·복원 아키텍처

타임라인 경계는 **0 / 4 / 7 / 12 / 19 / 27 / 30초**다. DESIGN.md §11의 자막과 내부 이벤트 시각을 사용한다.

| 장면 진입 시각 | 결정적으로 구성할 상태 |
|---|---|
| 0 | Overview, 장애 활성, 입력 없음, 분석 idle, 선택 없음, 계획 없음 |
| 4 | Operations Intelligence, 연결 맥락 표시, 분석 idle |
| 7 | 질문 입력 장면. 입력 문자열은 시각에서 파생; 9.2초에 전문 완성 |
| 12 | 질문 전문, 분석 done, 계산 결과, 전체 필터, 첫 페이지, 주문 미선택, 계획 없음 |
| 19 | 분석 done, LM-1001 선택과 근거, 계획 true, 결과 뷰 plan |
| 27 | End Card, 이전 결과는 저장하되 핵심 화면은 엔딩, Demo 배지 유지 |
| 30 | End Card 정지, playing=false, 추가 타이머 동작 없음 |

12~19초 안에서도 14.2초부터 LM-1001 선택 상태를 재구성한다. 11.4~12초는 분석 중, 19초 이후는 비교 상태다. 특정 시각으로 이동할 때 그 앞의 UI 클릭이 실제로 발생했는지에 의존하지 않는다.

- 단일 재생 시계의 경과 시간으로 현재 시각을 계산한다. 여러 `setTimeout`을 누적해 전체 길이를 맞추지 않는다.
- `stateAt(time)` 성격의 순수한 복원 경로가 초기 상태에서 시간순 명령을 적용한다. 분석 완료 명령은 공용 계산 함수를 호출한다. 표시용 타이핑·강조 진행률도 같은 시각에서 파생한다.
- 실시간 재생은 시계만 진행시키고 해당 시각의 상태를 투영한다. 완료 여부를 애니메이션 callback으로 결정하지 않는다.
- 일시정지 시 시계·타이핑·관계 강조·분석 피드백 진행을 함께 멈춘다. 재개 시 멈춘 시각을 기준으로 이어간다.
- 일반 UI에 수동 개입하면 일시정지한다. 재개 시 현재 타임라인 시각의 데모 상태를 복원한다는 동작을 제어 영역에 안내한다.
- 장면 이동은 목표 장면 시작 시각으로 이동하여 상태를 재구성한다. 재생 중 이동은 계속 재생, 정지 중 이동은 정지를 유지한다.
- `resetDemoState()`는 선택·필터·페이지·결과·계획·노드·재생 시각·입력 피드백·Record Mode까지 최초 상태로 복구한다. 기본 화면은 Operations Intelligence다. `30초 데모 시작`은 별도 명령으로 데모용 0초 상태(Overview)를 구성하고 재생한다. 새 데모 시작에서는 사용자가 선택한 Record Mode를 유지한다.
- 녹화 중 `R`은 0초로 재시작하는 단축 명령이다. 전체 초기화 리셋과 구분하여 Record Mode를 유지한다. 컨트롤의 `리셋`은 위 전체 초기화다.
- 페이지 숨김 시 재생을 일시정지하여 복귀 시 장면이 건너뛰지 않게 한다. 정확한 녹화는 전경 탭·1배속·중단 없는 재생에서 수행한다.
- 30,000ms에서 상태 시계를 종료한다. 렌더는 디스플레이의 다음 프레임에 반영될 수 있으므로 실제 영상 프레임에서 각 경계를 확인한다.

## 후속 구현: 기업 온톨로지 탐색 UX

- Explorer/엔딩의 정적 설명을 공통 `OntologyWorkbench`로 교체. 그래프·검색·시스템 필터·연결 강조·상세 패널의 선택 상태를 한곳에서 관리한다.
- `modelPresentation.ts`는 관계의 한국어 의미와 기존 seed에서 파생한 예시를 제공한다. 분석 로직과 원본 데이터 변경 없음.
- 그래프 노드/관계 버튼 및 상세 패널을 통해 키보드 탐색 가능. 모바일에서는 개념/관계 목록 사용.
- 엔딩은 generation 키로 재생/장면 재진입 시 탐색 상태를 초기화하고, 사용자 입력은 상위 컨트롤러를 일시정지한다.
- 검증: 기존 30초 3회 재생 및 전체 회귀, 검색 무결과/복구, 소스 필터, 관계 탐색, 데이터 예시, 연결 강조, 초기화와 수동 정지.
